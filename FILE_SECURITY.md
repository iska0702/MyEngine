# Защита файлов в Windows

Новые игровые архивы и сохранения используют AES-256-GCM через Windows CNG (BCrypt), с 128-битным тегом подлинности. Проверка тега выполняется до выдачи открытых данных и до распаковки. Ошибка ключа, изменение nonce, зашифрованных данных или контекста возвращает отказ и пустой результат. Запасного перехода на CBC для новых файлов нет.

## Форматы

- `content01.pak`–`content09.pak`: формат EPK3. Зашифрованы индекс, имена и содержимое файлов. Контекст каждого блока содержит имя файла из аутентифицированного индекса: блок одного файла нельзя переставить на место другого. Индексы имеют ограничения размеров и количества записей.
- `content10.pak`: формат SPK3 v2. Зашифрованы таблица текстур и каждый GDeflate-блок. Блок сначала читается через DirectStorage и проверяется/расшифровывается на CPU, затем передаётся из памяти в очередь DirectStorage для распаковки на GPU. Это добавляет CPU-обработку и копирование по сравнению с прежним прямым чтением открытого GDeflate с диска в GPU.
- Сохранения: SAVE v2. AES-GCM защищает сжатые данные, версию контекста и размеры. Обрезанные файлы, лишние байты и несовпадение размеров отклоняются; ошибка не заменяет текущую сцену.

96-битная часть случайного nonce и дополнительные 4 байта создаются системным криптографическим генератором. Все 16 байт также включены в AAD вместе с контекстом. Для каждого шифрования создаётся новый nonce; он не является секретом. GCM-тег хранится перед шифротекстом.

Старые SAVE v1 читаются редактором для миграции и при следующем сохранении записываются в SAVE v2. Исходные сцены и старые резервные копии не переписываются массово. Старый известный ключ оставлен только в явном CBC-считывателе для миграции; он не используется для новых архивов и сохранений. Релиз не принимает SAVE v1 как пользовательское runtime-сохранение; допускается только исходная стартовая сцена из аутентифицированного пакета. Для старого пользовательского сохранения сначала выполните миграцию через редактор, сохранив резервную копию.

## Ключ сборки

Общий постоянный ключ из исходников заменён случайным 32-байтным ключом, создаваемым на машине сборки. `tools/Security/ContentCrypto.ps1` хранит его в `.keys/content-key.dpapi` через Windows DPAPI CurrentUser и генерирует `src/Storage/GeneratedContentKey.h` перед компиляцией. Эти файлы исключены из Git; упаковщики не копируют их в дистрибутив. Пароль или ключ не печатается в журнал сборки. Если защищённое хранилище пропало, а сгенерированный заголовок остался, сборка завершается ошибкой вместо незаметной смены ключа.

Сохраните резервную копию ключевого материала в защищённом месте. DPAPI-файл связан с Windows-профилем и его DPAPI-ключами: простого переноса файла на другой компьютер недостаточно. Сгенерированный заголовок содержит открытые байты ключа и тоже является секретным исходным материалом. Не публикуйте его. Здесь нет автоматической ротации или переносимого менеджера ключей; случайная смена ключа сделает ранее записанные SAVE v2 недоступными новой сборке.

Из ключа шифрования через HMAC-SHA256 с отдельной меткой выводится другой ключ для HMAC манифеста DLL и лицензионного контейнера. Это симметричная проверка подлинности, а не цифровая подпись с публичным ключом. Криптографические ошибки не подменяются незащищённым FNV-хешем. MsQuic и остальные DLL дополнительно проверяются существующими средствами целостности; исполняемые EXE/DLL не зашифрованы AES, поскольку их загружает Windows.

## Проверки при запуске

Проверяются наличие и аутентификация индексов всех десяти томов; полезная нагрузка проверяется при чтении. Рендерер, лицензионная проверка и манифест используют общий ограниченный считыватель EPK3. В релизном `ReadContentBytes` виртуальные пути Content читаются из защищённых архивов. Файл `.complete` больше не считается доказательством целостности распакованного кэша: при каждом запуске кэш сверяется с аутентифицированными пакетами, изменённые файлы восстанавливаются.

Кэш содержит открытые файлы, необходимые WebView и импортерам. Шифрование не скрывает данные после их расшифровки в память и не гарантирует защиту от владельца машины с отладчиком: офлайн-игре нужен доступ к ключу, который включён в её бинарный код. GCM также не предотвращает откат на старый корректный файл с тем же ключом. Защита важных игровых решений остаётся на сервере.

Новый файловый криптобэкенд реализован для Windows. На других платформах он возвращает отказ, а не заменяет AES-GCM менее защищённым алгоритмом.

## Проверка

```powershell
pwsh -NoProfile -File ./tools/Diagnostics/CheckFileSecurity.ps1
```

Регрессия сравнивает результат с отдельным API .NET AesGcm, проверяет неверный ключ/тег/nonce/контекст, усечение и отсутствие открытого вывода при отказе, повреждение индекса и полезной нагрузки PAK, перестановку блоков между файлами, SAVE v2 и миграцию старой сцены редактора. Тесты работают с отдельными данными в Diagnostics и не изменяют сцены проекта.

Дополнительные проверки:

```powershell
./tools/Diagnostics/CheckFileProtection.ps1
./tools/Diagnostics/CheckProtectedBuild.ps1
./tools/Diagnostics/CheckStreamingSecurity.ps1
./tools/Diagnostics/CheckProtectedCache.ps1
```

Для тестов установленной сборки закройте движок. `CheckFileProtection` временно изменяет индексы архивов редактора и восстанавливает оригиналы в finally; `CheckProtectedCache` делает то же с локальным кэшем Test-проекта и требует предварительного запуска собранной игры. `CheckStreamingSecurity` работает с отдельной копией content10 в Diagnostics и проверяет загрузку тестовой текстуры DemoTexture через GPU DirectStorage.

Проверено 26.10.2026: обе полные сборки через build.bat (редактор и релиз Test-проекта) прошли. В редакторе проверены 69 ресурсов, в игре — 85 ресурсов и зашифрованный GDeflate-блок. Изменения индексов EPK3/SPK3 отклоняются проверкой запуска. Для текстуры 72×48 с семью mip-уровнями прошли аутентификация, расшифровка, распаковка и передача на GPU; изменённый тег не дошёл до GPU. Изменённый кэш восстановлен из PAK. Редактор и игра отрисовали кадры и завершились с кодом 0, исходная сцена проекта сохранена. Повреждённый существующий архив не затирается генератором манифеста. Отдельные ключевые файлы отсутствуют в дистрибутивах.

Журналы: Diagnostics/file-security-check.log, aes-startup-check.log, aes-editor-archives.log, aes-game-archives.log, aes-streaming-check.log, aes-cache-check.log, aes-editor-build.log, aes-project-build.log.

Документация используемого системного API: [Microsoft CNG — аутентифицированные режимы шифрования](https://learn.microsoft.com/en-us/windows/win32/api/bcrypt/ns-bcrypt-bcrypt_authenticated_cipher_mode_info).
